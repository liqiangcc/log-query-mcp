## 1. 执行摘要

本次预研验证了使用 Rust 和官方 `rmcp` SDK 实现日志查询 MCP 的可行性。

当前原型已经具备一条可运行的真实查询链路：

```text
JSON 日志来源配置
        ↓
SourceRegistry
        ↓
SafeRoot / openat2 安全文件访问
        ↓
有界流式扫描器
        ↓
结构化 MCP 搜索结果
        ↓
短期 match_ref / 分页 cursor
        ↓
有限上下文读取
```

自动化验证已覆盖：

- Streamable HTTP 和 stdio MCP 协议交互。
- 三个 MCP 工具的发现和调用。
- 真实日志文件搜索、分页和上下文读取。
- 路径穿越、软链接、特殊文件、轮转、替换和截断场景。
- 扫描字节、结果数、单行、上下文、响应大小和并发限制。
- RFC 3339 与自定义前缀时间戳。
- Linux 部署检查和基准烟测入口。

当前 CI 基线：

```text
rustfmt: passed
Clippy -D warnings: passed
Rust tests: 90 passed
stdio MCP smoke: passed
Streamable HTTP MCP smoke: passed
deployment doctor smoke: passed
benchmark smoke: passed
```

因此，Rust、`rmcp`、Tokio、Axum 和 `openat2()` 已足以支撑当前首期需求，可以进入正式工程化阶段。

但本次结果仍不足以直接宣布生产上线。目标 Linux 服务器上的性能、资源隔离、实际 AI 客户端兼容性和断连取消仍需完成，因此总体结论为：

> **CONDITIONAL GO：批准 Rust 技术栈进入正式实现；完成本报告第 12 节的上线前条件后，才能转为生产 GO。**

## 2. 预研目标与回答

### 2.1 Rust MCP SDK 是否够用

**结论：够用。**

当前项目只需要 tools-only Server、结构化输入输出、stdio 和 Streamable HTTP。官方 `rmcp` 已覆盖这些能力，并已在独立协议烟测中完成：

- 协议版本协商。
- 工具发现。
- 工具调用。
- 结构化结果。
- Streamable HTTP 会话 ID。
- SSE 响应解析。
- 会话删除。

项目不依赖 Prompts、Elicitation、Sampling 或 OAuth，因此 Rust SDK 尚未覆盖的其他协议边角能力不阻塞首期。

### 2.2 Streamable HTTP 是否适合远程日志 MCP

**结论：适合。**

服务部署在日志服务器上，客户端通过内网远程连接，因此 Streamable HTTP 比 stdio 更符合部署模型。stdio 保留用于本机调试和协议验证。

### 2.3 日志扫描是否能受控运行

**结论：核心方案可行。**

扫描器使用固定缓冲区和有界结果集合，不加载完整日志文件。已经验证：

- 字面量关键字跨读取缓冲区匹配。
- 中文 UTF-8。
- ASCII 大小写不敏感。
- 非法 UTF-8。
- CRLF。
- 超长单行。
- 扫描字节上限。
- 结果和响应内容上限。

真实生产吞吐仍需在目标磁盘和文件系统上测量。

### 2.4 文件访问边界是否可靠

**结论：在 Linux 5.6 及以上、受控目录权限前提下可行。**

核心方案为：

```text
预先打开白名单根目录 FD
+ 相对路径
+ openat2()
+ RESOLVE_BENEATH
+ RESOLVE_NO_SYMLINKS
+ RESOLVE_NO_MAGICLINKS
+ fstat 普通文件校验
```

该方案优于字符串前缀、一次性 `realpath` 或仅在最终文件设置 `O_NOFOLLOW`。

### 2.5 超时、取消和并发是否可控

**结论：核心原语可行，端到端断连取消仍需目标客户端验证。**

同步文件扫描通过 `spawn_blocking` 与 Tokio 控制面隔离，Semaphore 限制扫描并发，扫描循环协作检查 CancellationToken 和绝对 deadline。

### 2.6 match_ref 和 cursor 如何设计

**结论：首期采用单实例、服务端有状态、短期随机 token。**

- `match_ref` 绑定来源、相对路径、文件身份和匹配位置。
- cursor 绑定查询条件、候选文件快照、扫描位置和累计配额。
- 两类状态均具有 TTL、容量上限和淘汰。
- 服务重启后失效。
- 客户端不得解析 token 内部结构。

### 2.7 时间范围和轮转如何处理

**结论：来源级规则可行，精确性必须显式分级。**

- 查询范围使用 RFC 3339。
- 区间语义为 `[start_time, end_time)`。
- 可解析行按事件时间过滤。
- 无时间或畸形时间的匹配保守返回，时间字段为空。
- 文件名时间和 mtime 只用于候选排序，不伪造单条日志时间。

### 2.8 是否正式选择 Rust

**结论：选择 Rust。**

Rust 的价值主要在：

- 资源生命周期可预测。
- 文件描述符所有权明确。
- 并发状态更容易在类型层约束。
- 无 GC，适合受限内存和稳定延迟。
- Linux 系统调用集成自然。

选择 Rust 的前提是团队能够维护异步 Rust、系统调用和安全边界测试。

## 3. 当前架构

```text
┌─────────────────────────────────────────────┐
│ MCP Client / Local AI                       │
└──────────────────────┬──────────────────────┘
                       │ Streamable HTTP
┌──────────────────────▼──────────────────────┐
│ rmcp + Axum                                 │
│ list_log_sources / search_logs / context    │
└──────────────────────┬──────────────────────┘
                       │ typed request
┌──────────────────────▼──────────────────────┐
│ QueryService                                │
│ limits / timeout / pagination / response    │
└───────────────┬───────────────┬─────────────┘
                │               │
       ┌────────▼────────┐ ┌────▼─────────────┐
       │ SourceRegistry  │ │ State Stores     │
       │ admin config    │ │ match_ref/cursor │
       └────────┬────────┘ └──────────────────┘
                │
       ┌────────▼────────┐
       │ SafeRoot        │
       │ openat2 / fstat │
       └────────┬────────┘
                │ File
       ┌────────▼───────────────┐
       │ ScanExecutor           │
       │ Semaphore/spawn_blocking│
       └────────┬───────────────┘
                │
       ┌────────▼────────┐
       │ Streaming Scan │
       │ bounded memory │
       └────────────────┘
```

架构原则：

1. MCP 层不直接处理服务器路径。
2. 文件系统层不理解 MCP 请求。
3. 扫描器只处理 `Read` 和资源限制。
4. 引用和游标状态不能序列化到客户端。
5. 每一层均执行自己的边界校验。

## 5. 已确定技术决策

### 5.1 语言与 SDK

```text
Rust stable
rmcp 1.x（锁定 Cargo.lock）
Tokio
Axum
Serde / Schemars
rustix
```

### 5.2 MCP 传输

- 正式远程服务：Streamable HTTP。
- 本机调试：stdio。
- 默认监听回环地址；内网监听必须显式配置。

### 5.3 搜索语义

- 普通字面量子串。
- 中文 UTF-8 支持。
- 不区分大小写仅保证 ASCII case folding。
- 不支持正则、glob、Shell 或自定义查询语言。

### 5.4 文件范围

- AI 只提交 `source_id`。
- 路径和文件列表只能来自管理员配置。
- 首期使用显式相对文件列表。
- 目录 glob 自动发现后置。

### 5.5 查询引用

- match_ref 和 cursor 均为服务端有状态随机 token。
- 单实例内存存储。
- TTL 和容量有界。
- 重启后失效。

### 5.6 时间语义

- 请求时间使用 RFC 3339。
- 范围为 `[start, end)`。
- 未知时间结果保守返回。
- mtime 不能作为单条事件时间。

## 6. 安全结论

当前安全模型为：

```text
网络层限制谁能连接
MCP 层限制能调用哪些工具
配置层限制可选择哪些来源
文件系统层限制实际能打开哪些文件
运行账号和挂载权限限制进程能力
```

必须同时满足：

- Linux kernel >= 5.6。
- 非 root 运行。
- 日志和配置目录只读。
- 不可信用户不能向日志目录创建硬链接。
- 不调用 Shell 或外部 grep。
- 不允许旧内核静默降级为字符串路径检查。
- 错误响应不暴露绝对路径和系统堆栈。

Rust 提供内存与并发安全基础，但不能替代正确的目录权限、`openat2()` 和 systemd/cgroup 隔离。

## 7. 性能与资源结论

已经证明：

- 扫描内存不需要随文件大小线性增长。
- 扫描并发可以有界。
- 返回内容和 JSON 响应可以限制。
- 取消和 deadline 可以协作检查。
- 基准工具能完整扫描确定性文件并输出吞吐数据。

尚未证明：

- 目标磁盘上 1 GiB 和 10 GiB 文件的吞吐。
- 10,000 个小文件的发现和打开成本。
- 1、4、8 并发下的 CPU、RSS 和 P99。
- 冷页缓存与热页缓存差异。
- 真实客户端断连后的取消延迟。

因此当前默认限制仍应视为候选值，不应直接作为生产 SLA。

## 8. 需求文档修改建议

正式开发前建议将以下内容同步回 `REQUIREMENTS.md`：

1. 部署前提明确为 Linux kernel 5.6 及以上。
2. 时间区间明确为 `[start_time, end_time)`。
3. 不区分大小写首期仅保证 ASCII。
4. 未知或畸形时间的匹配保守返回，`timestamp=null`。
5. match_ref 和 cursor 为短期单实例状态，服务重启后失效。
6. 首期日志来源使用显式文件列表；目录 glob 自动发现后置。
7. `newest_first` 在真实链路完成前不应写入首期验收范围。
8. 压缩日志、实时 tail 和多实例共享状态继续保持非首期范围。
9. 资源限制应允许配置，但客户端只能缩小、不能扩大服务端上限。
10. 真实上线验收增加客户端兼容、性能和 systemd 资源隔离用例。

## 9. 已知限制

- `newest_first` 尚未接入真实前向扫描链路。
- 文件仍需显式配置，未实现目录 glob 自动发现。
- 查询资源限制主要采用代码和 JSON 配置基线，尚未形成生产调优值。
- 暂无配置热加载。
- 多实例不共享 match_ref 和 cursor。
- 没有全文索引；查询成本与扫描数据量相关。
- 没有认证、来源授权和 TLS，依赖受控内网前提。
- 不支持压缩日志、Kubernetes、Loki 或 Elasticsearch。

## 10. 技术风险

| 风险 | 严重度 | 当前措施 | 后续动作 |
|---|---:|---|---|
| 目标内核不支持 openat2 | 高 | doctor 检查 | 部署前硬性检查 |
| 日志目录可被非可信用户写入 | 高 | 只读运行建议 | 权限与挂载审计 |
| 大文件查询占用磁盘 I/O | 高 | 扫描字节/并发/deadline | 目标环境基准和 cgroup |
| 客户端断连后任务继续 | 中 | CancellationToken 原语 | 端到端断连测试 |
| SDK 升级引入协议回归 | 中 | Cargo.lock 与协议烟测 | 升级门禁 |
| 多实例 token 不共享 | 中 | 首期单实例 | 后续粘性或共享状态 |
| 服务器时钟偏差 | 中 | 稳定排序但不声称因果 | 时间同步与结果提示 |
| 明文日志含敏感信息 | 中 | 来源白名单 | 管理员审计与后续脱敏 |

## 11. 正式实现建议

不要直接把预研分支视为生产版本。建议：

1. 从 `main` 创建正式实现分支。
2. 以当前 POC 为参考，按模块迁移并重新评审。
3. 保留协议烟测、安全测试和基准工具。
4. 将配置、错误模型、资源限制和可观测性作为正式 API 设计。
5. 在合并前完成需求文档同步和 ADR 审核。

首期正式实现顺序：

```text
配置模型冻结
→ MCP Schema 冻结
→ 安全文件发现
→ 多文件搜索编排
→ 上下文与分页
→ 部署和可观测性
→ 目标环境验收
```

## 12. 生产 GO 条件

以下条件全部满足后，才建议生产上线：

1. 目标服务器确认 Linux kernel >= 5.6。
2. MCP Inspector 和至少一个实际 AI 客户端完成三工具验证。
3. 1 GiB、10 GiB 和 10,000 小文件基准完成。
4. 1、4、8 并发下采集 CPU、RSS、吞吐和 P99。
5. 客户端断连后扫描任务能在目标时间内退出。
6. 日志持续追加、轮转、截断和删除压力测试通过。
7. systemd 的用户、只读路径、内存、CPU 和 FD 限制实测通过。
8. 明确是否启用 `RESOLVE_NO_XDEV`。
9. 更新需求文档，使其与实际时间、分页、大小写和部署语义一致。
10. 决定 `newest_first` 是正式实现还是从首期 Schema 移除。
