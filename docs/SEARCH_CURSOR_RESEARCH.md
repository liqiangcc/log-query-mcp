# R-08 分页游标预研

> 状态：核心 POC 已通过自动化测试  
> 实现：`src/search_cursor.rs`

## 1. 目标

当日志匹配结果超过单次返回上限时，AI 需要继续获取后续结果。游标能力必须满足：

- 不向客户端暴露服务器路径、inode、文件偏移或候选文件列表。
- 不能通过修改游标改变查询范围。
- 不能把一个查询的游标用于另一个查询。
- 日志轮转、文件替换或截断后不能错误地从新文件继续。
- 游标数量和生命周期必须有界。
- 服务重启后游标失效可以被首期接受。

## 2. 方案选择

本阶段比较两种方案：

### 2.1 服务端有状态游标

客户端只持有随机 token；候选文件快照、文件身份和扫描位置保存在服务端内存。

优点：

- 实现简单，安全边界清晰。
- 不需要把内部路径和偏移编码到客户端 token。
- 易于绑定完整查询条件。
- 易于设置 TTL、容量和淘汰策略。

缺点：

- 服务重启后失效。
- 多实例需要会话粘性或共享状态。
- 占用有限服务端内存。

### 2.2 签名无状态游标

将位置和查询摘要编码到 token 中并签名。

优点：服务端状态较少。  
缺点：编码格式、密钥轮换、日志变化语义和信息泄露面更复杂。

**首期选择服务端有状态游标。**

## 3. 客户端可见格式

POC 使用 UUID v4 生成：

```text
cur_<32 个十六进制字符>
```

例如：

```text
cur_b4a6e7490cce40e7905f9a92464fc5aa
```

游标本身不包含：

- 日志来源。
- 搜索关键字。
- 时间范围。
- 文件路径。
- 文件名。
- 设备号和 inode。
- 当前文件索引和字节偏移。

## 4. 查询条件绑定

游标内部保存并绑定：

```text
source_ids
keyword
case_sensitive
start_time
end_time
order
max_results
```

客户端继续查询时必须提交与原请求一致的查询条件和游标。任何条件变化均返回 `QueryMismatch`，包括：

- 更换日志来源。
- 修改关键字。
- 改变大小写规则。
- 改变时间范围。
- 改变排序方向。
- 改变分页大小。

该设计与当前 `SearchLogsRequest` 兼容，不需要额外增加新的 MCP 工具。

## 5. 候选文件快照

服务端内部游标保存候选文件快照：

```text
source_id
relative_path
file_identity { device, inode }
file_size_at_snapshot
```

并保存继续位置：

```text
next_candidate_index
next_byte_offset
next_line_number
files_scanned
bytes_scanned
results_returned
```

内部状态不实现 Serde 序列化，避免路径和偏移意外进入 MCP 响应。

候选文件数量设置硬上限，POC 当前为：

```text
10,000 个候选文件
```

正式默认值应结合单次最大扫描文件数确定，通常应更低。

## 6. 文件变化处理

继续扫描当前候选文件前，服务端：

1. 根据来源找到对应 `SafeRoot`。
2. 使用 `openat2()` 安全重新打开相对路径。
3. 校验设备号和 inode。
4. 校验当前文件大小不小于继续偏移。

行为：

- 文件追加：允许继续。
- 文件被同名替换：返回 `FileChanged`。
- 文件轮转后同名新文件出现：返回 `FileChanged`。
- 文件被截断到继续位置之前：返回 `FileTruncated`。
- 文件不存在或不能安全打开：返回安全打开错误。

对于同 inode 原地改写且文件大小仍覆盖偏移的情况，当前游标只能提供尽力而为语义。正式实现可以通过记录偏移附近短哈希进一步检测内容变化，但该增强不属于首期必要能力。

## 7. 游标生命周期

`SearchCursorStore` 提供：

- 固定容量。
- 固定 TTL。
- 过期自动清理。
- 达到容量时淘汰最旧游标。
- 服务重启后全部游标失效。
- 未知、格式错误、过期和淘汰游标统一返回 `UnknownOrExpired`。

初始建议：

```text
游标 TTL：10 分钟
全局容量：1,000 个活动游标
```

最终值应根据最大并发查询数和真实分页使用率确定。

## 8. 游标推进

POC 提供原子替换操作：

```text
旧 token + 原查询条件 + 新位置
        ↓
旧 token 失效
新 token 生效
```

因此每个成功返回的后续页面都使用新的 `next_cursor`。

查询已经结束时，调用 `complete` 删除游标，不再返回 `next_cursor`。

这种方式可以减少旧位置被长期重复使用。并发重复提交同一个旧游标时，只有第一个成功推进的请求能够替换它；正式 MCP 层应把这种冲突统一表现为游标失效，并允许 AI 重新执行原查询。

## 9. 累计资源限制

游标保存累计：

- 已扫描文件数。
- 已扫描字节数。
- 已返回结果数。

正式编排层必须用这些累计值限制整个分页查询，而不是让每一页重新获得完整扫描配额。否则客户端可以通过不断翻页绕过：

- 最大扫描字节数。
- 最大扫描文件数。
- 最大总结果数。
- 最长查询生命周期。

单页返回数量仍由 `max_results` 控制。

## 10. 已验证用例

自动化测试覆盖：

- 创建不可预测且不含路径信息的游标。
- 正常解析游标状态。
- 修改关键字后拒绝使用原游标。
- 原子替换后旧游标失效，新游标生效。
- 查询完成后删除游标。
- TTL 到期失效。
- 容量上限淘汰最旧游标。
- 新 Store 模拟服务重启后旧游标失效。
- 拒绝 `..` 路径、错误日志来源和越界偏移。
- 未变化文件可以安全重新打开。
- 同名文件替换后拒绝继续。
- 原文件被截断后拒绝继续。
- 拒绝零容量和零 TTL。

## 11. 当前结论

R-08 核心技术结论为 **GO**：

- 服务端有状态游标适合首期单实例内网服务。
- 查询条件绑定能够阻止跨查询复用。
- 候选文件快照和文件身份校验能够处理主要轮转场景。
- TTL、容量和累计统计能够形成资源边界。
- 不需要在客户端 token 中暴露或签名内部路径状态。
