# R-08 服务端有状态搜索游标预研

> 状态：核心 POC 已通过严格 CI  
> 实现：`src/search_cursor.rs`、`src/cursor_reader.rs`

## 1. 目标

当日志匹配数量超过单次返回上限时，AI 需要继续获取后续结果，同时不能通过游标：

- 修改原查询条件。
- 选择任意日志文件。
- 构造任意文件偏移。
- 绕过日志来源白名单。
- 在日志轮转后读取同名新文件。
- 把游标创建后追加的日志混入旧查询。
- 并发消费同一个游标并生成两个有效分支。

R-08 验证首期采用服务端有状态游标的可行性。

---

## 2. 方案结论

首期采用服务端有状态游标。

客户端只看到不可预测的短期 token：

```text
cur_<随机 UUID>
```

真实状态保存在服务端内存中：

```text
原查询条件
候选文件快照
当前候选文件序号
当前文件下一次读取的字节偏移
当前文件下一行行号
累计扫描文件数
累计扫描字节数
累计返回结果数
过期时间
租约状态
```

首期不采用签名无状态游标，因为它会额外引入密钥管理、token 版本兼容、内部文件信息编码和更复杂的日志轮转语义。

---

## 3. 查询条件绑定

`SearchCursorQuery` 绑定：

- `source_ids`
- `keyword`
- `case_sensitive`
- `start_time`
- `end_time`
- `order`
- `max_results`

继续查询时，服务端从请求重新构造查询快照，并与游标中的快照精确比较。

以下任一变化都会返回 `QueryMismatch`：

- 更换关键字。
- 增加、删除或重排日志来源。
- 修改大小写选项。
- 修改时间范围。
- 修改排序方向。
- 修改单页结果数量。

客户端提交的 `cursor` 字段本身不进入查询快照。

---

## 4. 候选文件快照

首次查询在扫描前生成稳定候选文件列表。

每个候选文件保存：

```text
source_id
relative_path
file_identity { device, inode }
file_size_at_snapshot
```

约束：

- 候选来源必须属于原查询。
- 路径必须是来源根目录内的规范化相对路径。
- 禁止绝对路径、`.` 和 `..`。
- 同一个来源和相对路径不能重复。
- POC 候选文件硬上限为 500。

候选文件顺序决定分页顺序，后续页面不能重新发现并插入新文件。

---

## 5. 游标位置与累计预算

游标位置包含：

```text
next_candidate_index
next_byte_offset
next_line_number
```

语义：

- `next_candidate_index`：下一页继续处理的候选文件。
- `next_byte_offset`：下一次读取的行起始字节位置。
- `next_line_number`：该位置对应的行号，从 1 开始。

当前不变量包括：

```text
files_scanned == next_candidate_index
next_candidate_index < candidates.len()
next_byte_offset <= file_size_at_snapshot
next_line_number >= 1
bytes_scanned >= next_byte_offset
```

续查状态只能向前推进：

- 候选文件序号不能后退。
- 同一文件内字节偏移必须增加。
- 同一文件内行号不能后退。
- 累计文件数、字节数和结果数不能减少。
- 查询条件和候选快照不能变化。

当前候选文件已经处理完成时，应推进到下一个文件；最后一个文件完成后直接结束游标，不创建指向 EOF 的后继游标。

累计计数用于后续编排器限制整个逻辑查询的资源消耗，避免每一页重新获得完整扫描预算。

---

## 6. 单次消费租约

`SearchCursorStore::begin` 为单次页面请求创建租约。

行为：

1. 校验 token、TTL 和查询条件。
2. 标记游标正在消费。
3. 并发使用同一 token 的请求返回 `Busy`。
4. 页面构造成功后调用 `commit`。
5. `commit` 原子删除旧 token，并可创建一个新的后继 token。
6. 最后一页调用 `commit(None)`，只删除旧 token。
7. 页面构造失败或 Future 被丢弃时，租约 Drop 自动释放，旧 token 可以重试。

状态提交失败的页面不得返回给客户端，避免同一个游标产生两个有效后继分支。

Store 还支持：

- 固定容量。
- 固定 TTL。
- 过期清理。
- 淘汰最旧的未租用游标。
- 所有槽位都被活跃租约占用时返回 `CapacityBusy`。
- 服务重启后游标失效。

---

## 7. 文件变化语义

续查时，服务端根据 `source_id` 选择对应 `SafeRoot`，再通过 `openat2()` 重新打开候选文件。

`open_cursor_file` 校验：

- 设备号和 inode 与快照一致。
- 当前文件大小不能小于 `file_size_at_snapshot`。

因此：

- 日志轮转并创建同名新文件：游标失效。
- 文件被替换：游标失效。
- 文件被截断到快照大小以下：游标失效。
- 文件删除或无法安全打开：游标失效。

文件追加允许发生，但追加内容不属于旧查询。

---

## 8. 快照范围读取

`open_cursor_snapshot_reader` 将文件变化校验、续查位置校验和读取上限组合成一个受控 Reader。

它执行：

1. 调用 `open_cursor_file` 验证文件身份和快照大小。
2. 验证 `next_byte_offset` 之前一个字节是换行符，或偏移为 0。
3. 拒绝位于日志行中间的续查偏移。
4. 拒绝位于快照 EOF 的游标。
5. 跳转到 `next_byte_offset`。
6. 使用 `Take<File>` 将读取上限固定为：

```text
file_size_at_snapshot - next_byte_offset
```

即使底层文件继续追加，Reader 也会在原快照末尾返回 EOF。

这把“不得读取追加内容”从调用约定变成了代码层硬约束。

---

## 9. 已覆盖的自动化用例

- 创建不可预测 token，且 token 不包含服务名、路径或关键字。
- 查询条件变化后拒绝复用游标。
- 同一 token 不能并发消费。
- 租约 Drop 后允许重试。
- 成功翻页后旧 token 原子失效。
- 最后一页完成后删除游标。
- 不合法后继状态不会破坏原游标。
- 活跃游标不会因容量压力被淘汰。
- TTL 到期、容量淘汰和服务重启后游标失效。
- 拒绝路径穿越、未知来源和重复候选文件。
- 拒绝超出快照的字节偏移和倒退的累计计数。
- 候选快照和查询条件不能在后继状态中变化。
- 日志追加后仍可打开原快照。
- 日志替换或截断后拒绝继续。
- 快照 Reader 不读取游标创建后追加的日志。
- 拒绝位于日志行中间的续查偏移。
- 拒绝指向快照 EOF 的后继游标。

## 10. 当前结论

R-08 核心方案结论为 **GO**。

已验证：

- 游标不可预测并与原查询条件绑定。
- 候选文件和续查位置只保存在服务端。
- TTL、容量和单次消费租约有效。
- 旧游标在成功翻页后原子失效。
- 文件轮转、替换和截断可检测。
- 续查偏移必须位于行边界。
- 分页读取被硬限制在原文件快照范围内。

正式接入 MCP 前仍需完成：

1. 管理员日志来源配置和候选文件发现。
2. 多来源候选文件稳定排序。
3. 将累计扫描预算接入实际扫描编排器。
4. 把 `SearchCursorStore` 作为 MCP Server 共享状态。
5. 在真实 `search_logs` 中实现首次页面和后续页面。
6. 先提交游标状态，再返回 MCP 页面。
7. 验证 `oldest_first` 和 `newest_first` 的完整分页顺序。
8. 限制完整 MCP JSON 响应大小。

首期继续采用单实例内存游标，并接受服务重启后失效。
