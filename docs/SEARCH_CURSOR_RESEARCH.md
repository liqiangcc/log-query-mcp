# R-08 服务端有状态搜索游标预研

> 状态：核心 POC 已通过严格 CI  
> 实现：`src/search_cursor.rs`

## 1. 目标

当日志匹配数量超过单次返回上限时，AI 需要继续获取后续结果，同时不能通过游标：

- 修改原查询条件。
- 选择任意日志文件。
- 构造任意文件偏移。
- 绕过日志来源白名单。
- 在日志轮转后错误读取同名新文件。

R-08 验证首期采用服务端有状态游标的可行性。

---

## 2. 方案选择

### 2.1 已选方案：服务端有状态游标

客户端可见值为不可预测的短期 token：

```text
cur_<随机 UUID>
```

客户端不能解析或构造 token 内部状态。

游标真实状态保存在服务端内存中，包括：

```text
原查询条件
候选文件快照
当前候选文件序号
当前文件下一次读取的字节偏移
当前文件下一行行号
累计扫描文件数
累计扫描字节数
累计返回结果数
过期时间
```

### 2.2 暂不采用：签名无状态游标

无状态游标需要把来源、文件身份、偏移和查询摘要编码到客户端 token 中，再进行签名和版本管理。

对于首期，它会额外引入：

- 密钥管理。
- token 版本兼容。
- 更复杂的日志轮转语义。
- 内部文件信息泄露风险。
- 更复杂的大小控制。

因此首期不采用。

---

## 3. 查询条件绑定

`SearchCursorQuery` 绑定以下参数：

- `source_ids`
- `keyword`
- `case_sensitive`
- `start_time`
- `end_time`
- `order`
- `max_results`

继续查询时，服务端根据客户端请求重新构造查询快照，并与游标中的快照进行精确比较。

任何字段变化都返回：

```text
QueryMismatch
```

这意味着以下操作均不允许：

- 使用旧游标更换关键字。
- 增加或删除日志来源。
- 更换排序方向。
- 更改时间范围。
- 更改单页结果数量。

`source_ids` 的顺序也是查询快照的一部分。正式 MCP 工具应保持首次请求中的来源顺序，不在客户端侧重新排序。

---

## 4. 候选文件快照

首次查询在开始扫描前生成稳定的候选文件列表。

每个候选文件至少保存：

```text
source_id
relative_path
file_identity { device, inode }
file_size_at_snapshot
```

候选文件顺序决定分页顺序，因此必须由服务端按照查询排序规则一次性生成，后续页面不能重新发现并插入新文件。

候选路径是日志来源根目录内的规范化相对路径，不允许：

- 绝对路径。
- `.`。
- `..`。
- 查询来源之外的 `source_id`。

当前 POC 的候选文件硬上限为：

```text
10,000
```

正式默认值仍应服从服务端的单次最大扫描文件数配置。需求文档建议默认值为 500，因此生产配置不应直接使用 POC 硬上限。

---

## 5. 游标位置

游标记录：

```text
next_candidate_index
next_byte_offset
next_line_number
```

语义为：

- `next_candidate_index`：下一页应继续处理的候选文件。
- `next_byte_offset`：该文件下一次读取的行起始字节位置。
- `next_line_number`：该位置对应的行号，从 1 开始。

服务端生成下一页时必须从该位置继续，而不是从文件开头重新搜索。

当前游标数据会校验：

- 候选文件列表不能为空且不能超过上限。
- 当前候选文件序号必须有效。
- 下一行行号必须大于 0。
- 下一字节偏移不能超过文件快照大小。
- 已扫描文件数不能超过候选文件总数。

正式编排器还应维持以下更强不变量：

```text
files_scanned == next_candidate_index
```

当前候选文件读取完成后，应立即推进到下一个候选文件；不应创建指向已完成文件 EOF 的新游标。

---

## 6. 文件变化语义

继续查询时，服务端根据游标中的 `source_id` 选择对应 `SafeRoot`，再使用 `openat2()` 重新打开候选文件。

当前 POC 校验：

- 当前设备号和 inode 必须与候选快照一致。
- 当前文件大小必须仍覆盖续查偏移。

因此：

- 日志轮转并创建同名新文件：游标失效。
- 文件被截断到续查偏移之前：游标失效。
- 文件被删除或无法安全打开：游标失效。

### 6.1 文件追加

日志追加不会改变原文件 inode，因此允许继续查询。

但续查扫描必须以：

```text
file_size_at_snapshot
```

作为该候选文件的读取上界，不得把游标创建后追加的新日志混入旧查询。

新追加内容应由新的 `search_logs` 查询获取。

### 6.2 文件缩短

生产实现应要求当前文件大小至少仍为 `file_size_at_snapshot`。如果文件从尾部被截断，即使 `next_byte_offset` 仍然存在，也应使游标失效，避免静默漏掉快照中的剩余内容。

当前 POC 只验证文件大小覆盖 `next_byte_offset`；在接入真实分页扫描器前应加强为快照大小校验。

## 7. 游标生命周期

`SearchCursorStore` 提供：

- 固定容量。
- 固定 TTL。
- 插入时清理过期项。
- 达到容量时淘汰最旧游标。
- 服务重启后游标自然失效。
- 格式错误、未知和过期游标统一返回 `UnknownOrExpired`。

首期接受：

- 单实例部署。
- 服务重启后游标失效。
- 不保证跨实例使用游标。

多实例部署时，必须选择以下一种方式：

1. MCP 会话保持实例粘性；或
2. 使用共享游标存储。

首期不引入共享存储。

---

## 8. 单次使用与并发调用

`replace()` 会在同一个锁内完成：

1. 校验旧游标仍存在且查询条件一致。
2. 删除旧游标。
3. 创建新的随机游标。
4. 保存下一续查位置。

因此旧游标在成功产生下一游标后立即失效。

实际 MCP 分页流程必须遵守：

```text
解析旧游标
    ↓
扫描并构造下一页
    ↓
原子 replace 或 complete
    ↓
只有状态提交成功后才返回页面
```

如果两个请求并发使用同一个游标，它们可能重复执行部分扫描，但只有一个请求能成功提交游标状态。状态提交失败的请求不得向客户端返回其结果。

这保证客户端不会通过重放同一游标获得两个有效的后继分支。

---

## 9. 资源限制

游标保存累计计数：

- `files_scanned`
- `bytes_scanned`
- `results_returned`

这些计数用于后续编排器执行整个逻辑查询的累计资源限制。

正式实现需要明确：

- 单页结果数量由 `max_results` 控制。
- 单页响应大小仍受 MCP 响应上限控制。
- 整个游标生命周期的累计扫描文件数和扫描字节数不能无限增长。
- 游标过期后不能恢复累计预算。

不能把每一页都当作一个全新的、拥有完整扫描预算的查询，否则客户端可以通过分页绕过服务端资源限制。

## 10. 已覆盖的自动化用例

当前测试覆盖：

- 创建不透明游标并恢复服务端状态。
- token 不包含服务名和文件名。
- 修改关键字后拒绝复用游标。
- 原子替换游标并使旧 token 失效。
- 查询完成后删除游标。
- TTL 到期后游标失效。
- 达到容量后淘汰最旧游标。
- 新 Store 模拟服务重启后旧游标失效。
- 拒绝路径穿越候选文件。
- 拒绝查询来源之外的候选文件。
- 拒绝超过文件快照的字节偏移。
- 安全重新打开未变化文件。
- 文件轮转或替换后拒绝继续。
- 文件截断到续查位置之前后拒绝继续。
- 拒绝为零的 Store 容量和 TTL。

## 11. 当前结论

R-08 核心方案结论为 **CONDITIONAL GO**。

已经验证：

- 游标不可预测。
- 游标与原查询条件绑定。
- 候选文件和续查位置保存在服务端。
- TTL 和容量限制有效。
- 旧游标可以在成功翻页后原子失效。
- 文件轮转、替换和严重截断能够被检测。

在正式接入 MCP 前必须完成：

1. 候选文件发现和稳定排序。
2. 按 `file_size_at_snapshot` 限制续查读取范围。
3. 文件缩短到快照大小以下时使游标失效。
4. 校验续查偏移位于日志行边界。
5. 强制累计扫描预算。
6. 先提交游标状态，再返回 MCP 页面。
7. 实现真实 `search_logs` 分页编排。
8. 验证 `oldest_first` 和 `newest_first` 的实际文件与行扫描顺序。

首期继续采用服务端有状态游标，不采用无状态签名 token。
