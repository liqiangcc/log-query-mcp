# R-09 时间范围与日志时间戳预研

> 状态：时间戳解析 POC 已实现，待真实扫描链路和轮转验证  
> 实现：`src/timestamp.rs`

## 1. 目标

问题排查通常包含大致发生时间。R-09 需要验证：

- 日志来源能否配置时间戳格式和时区。
- 带时区和不带时区日志能否统一为绝对时间。
- 多行异常堆栈能否继承上一条事件时间。
- 查询时间范围的边界语义是否明确。
- 无法解析时间戳时是否能够安全退化，而不是伪造时间。

## 2. 首期支持格式

POC 先支持两类常见格式。

### 2.1 RFC 3339

示例：

```text
2026-06-19T14:20:03.125+09:00 ERROR payment failed
```

时间戳自身包含 UTC 偏移，不允许额外配置来源级偏移。

### 2.2 年月日时分秒毫秒

示例：

```text
2026-06-19 14:20:03.125 ERROR payment failed
```

该格式不包含时区，因此日志来源必须配置固定 UTC 偏移，例如：

```text
+09:00 = 32400 秒
```

首期不自动读取服务器本地时区，避免部署环境变化导致相同日志被解释成不同绝对时间。

## 3. 来源级规则

```rust
TimestampRule {
    format,
    prefix_bytes,
    local_offset_seconds,
    inherit_previous,
}
```

说明：

- `format`：两种首期格式之一。
- `prefix_bytes`：时间戳位于日志行开头时的固定字节长度。
- `local_offset_seconds`：仅无时区格式使用。
- `inherit_previous`：无时间戳续行是否继承上一条时间。

首期要求时间戳位于日志行前缀，不尝试在任意位置猜测时间。

## 4. 多行异常

异常堆栈通常只有首行包含时间：

```text
2026-06-19 14:20:03.125 ERROR PaymentAuthException
    at payment::authorize(payment.rs:42)
Caused by: HttpException: forbidden
```

启用 `inherit_previous=true` 后：

- 首行解析并更新当前事件时间。
- 后续无时间戳行继承该时间。
- 继承结果明确标记 `inherited=true`。

该语义适合按行扫描的异常堆栈，但仍是启发式规则。日志来源格式不满足该假设时应关闭继承。

## 5. 时间范围

POC 使用包含两端的范围：

```text
start <= timestamp <= end
```

支持：

- 只有开始时间。
- 只有结束时间。
- 同时提供开始和结束时间。
- 不提供范围。

开始时间晚于结束时间时直接拒绝配置或请求。

正式 MCP 层应把输入的 RFC 3339 字符串在进入扫描器前解析成绝对时间，避免在每一行重复解析查询参数。

## 6. 无法解析的日志行

解析失败时不伪造时间：

- 开启继承且已有上一条有效时间：使用继承时间。
- 未开启继承：返回无时间。
- 开启继承但尚无上一条有效时间：返回无时间。

时间过滤对“无时间”结果的最终策略仍需按来源确定。候选方案：

1. 严格模式：排除无法确定时间的匹配。
2. 保守模式：返回匹配，但 `timestamp=null`。

面向问题排查，首期建议采用保守模式，避免漏掉异常堆栈或格式偶发变化的关键日志。

## 7. 文件修改时间退化

日志来源没有行级时间规则时，可以使用文件修改时间筛选候选文件，但必须明确：

- 文件修改时间不是日志事件时间。
- 它只能缩小候选文件集合。
- 不能据此给单条结果生成时间戳。
- 当前活动日志的修改时间会持续变化。

该退化逻辑尚未在 POC 中实现。

## 8. 自动化测试

当前测试覆盖：

- RFC 3339 前缀解析。
- 本地毫秒格式和来源级 `+09:00` 偏移。
- 堆栈续行继承时间。
- 关闭继承时无时间续行保持未知。
- 时间范围包含起止边界。
- 排除范围之外的纳秒时间。
- 拒绝零长度前缀。
- 拒绝无时区格式缺少来源偏移。
- 拒绝 RFC 3339 额外配置本地偏移。
- 拒绝开始时间晚于结束时间。

## 9. 当前结论

R-09 时间戳解析核心方向为 **GO**：

- 来源级固定格式比全局猜测更可控。
- 带时区和无时区格式可以统一为绝对时间。
- 堆栈续行继承能够覆盖首期异常排查场景。
- 解析失败可以保持未知，不需要伪造时间。

## 11. 首期建议

建议首期只提供经过验证的格式枚举，而不是直接允许管理员填写任意时间格式表达式。

当真实日志样本证明两种格式不足时，再增加新的显式格式类型或经过校验的自定义格式能力。
