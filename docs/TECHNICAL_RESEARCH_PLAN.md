# 日志查询 MCP 技术预研计划

> 版本：v1.0  
> 日期：2026-06-19  
> 状态：待执行  
> 目标技术栈：Rust + 官方 `rmcp` SDK + Streamable HTTP

---

## 1. 预研目的

本次预研不以完成正式产品为目标，而是验证当前需求能否基于 Rust 和官方 MCP Rust SDK 稳定实现，并为后续技术方案和正式开发提供可复现的决策依据。

预研结束后必须能够回答以下问题：

1. 官方 Rust MCP SDK 是否能够满足本项目三个工具的实现和客户端调用需求？
2. Streamable HTTP 是否能够在目标内网和实际 AI 客户端中稳定工作？
3. 日志文件扫描是否能够在限定内存、时间和并发条件下运行？
4. 是否能够可靠阻止路径穿越、软链接逃逸和特殊文件读取？
5. 请求取消、查询超时和资源上限是否能够真正终止扫描任务？
6. `match_ref` 和分页游标应采用怎样的首期设计？
7. 时间范围、日志轮转和上下文读取的实现边界是什么？
8. Rust 是否应被确定为正式实现语言，还是需要切换到 Go 等其他方案？

预研最终应形成明确结论：

```text
GO          使用 Rust 进入正式开发
CONDITIONAL 在补充指定约束后使用 Rust
NO-GO       放弃 Rust 或当前 SDK，改用其他实现方案
```

---

## 2. 已确定的前提

### 2.1 产品前提

- 服务部署在能够读取日志文件的 Linux 服务器上。
- 服务仅在受控内网中使用。
- 首期不实现客户端认证、日志来源级授权和 TLS。
- MCP 只提供只读日志搜索，不执行 Shell 命令。
- AI 只能提交 `source_id`，不能提交服务器路径。
- 首期工具为：
  - `list_log_sources`
  - `search_logs`
  - `get_log_context`
- 首期只支持普通文本日志和未压缩轮转日志。
- 首期搜索采用字面量子串匹配，不支持正则表达式。

### 2.2 技术基线

预研默认采用：

| 类别 | 候选技术 |
|---|---|
| 语言 | Rust stable |
| MCP SDK | 官方 `rmcp` |
| 异步运行时 | Tokio |
| HTTP | Axum + Streamable HTTP |
| 序列化 | Serde / serde_json |
| JSON Schema | Schemars |
| 安全文件访问 | rustix + Linux `openat2()` |
| 日志与追踪 | tracing / tracing-subscriber |
| 错误处理 | thiserror |
| 基准测试 | Criterion、自定义集成基准、系统指标采集 |

截至 2026-06-19，官方 MCP 文档将 Rust SDK 标记为 Tier 2；官方路线图显示服务端一致性为 87.5%。当前未完成项主要涉及 Prompts、Elicitation 和 Streamable HTTP 的 Host/Origin 校验。前两项不在本项目范围内，HTTP 校验需要在预研中单独确认影响。

官方 `rmcp` 已提供工具宏、输入/输出 Schema、stdio、Streamable HTTP Server 和 Tokio 异步运行时支持，具备本项目 POC 所需的协议能力。

### 2.3 Linux 前提

安全文件打开优先采用 `openat2()`，因此预研目标环境为：

```text
Linux kernel >= 5.6
```

如果目标服务器存在更低版本内核，预研必须单独给出兼容方案；不得静默退化为仅依赖字符串前缀或一次性 `realpath` 校验的实现。

## 3. 预研范围

### 3.1 本次必须验证

- Rust 工程和基础 CI。
- `rmcp` 工具定义、发现和调用。
- Streamable HTTP 远程连接。
- 结构化输入和结构化输出。
- 普通字符串日志搜索。
- 单文件和目录日志来源。
- 多日志来源搜索。
- 有限上下文读取。
- 查询超时和主动取消。
- 文件数、扫描字节数、结果数、单行和响应大小限制。
- `openat2()` 路径边界和软链接防护。
- 日志追加、轮转、截断和删除场景。
- `match_ref` 和分页游标的最小可行方案。
- 基础吞吐、内存、CPU、并发和取消延迟。
- systemd 运行和非 root 只读权限。

### 3.2 本次不做

- 完整生产功能开发。
- 用户认证和权限系统。
- TLS。
- Loki、Elasticsearch 或 Kubernetes 适配。
- 实时 tail/follow。
- 压缩日志查询。
- 正则表达式或复杂查询语言。
- 自动异常聚合和根因分析。
- Web 管理后台。
- 多节点分布式游标。
- 长期持久化索引。

## 4. 预研方法

每个预研项均应包含：

1. **待验证问题**：明确技术不确定性。
2. **最小实验**：只实现验证该问题所需的代码。
3. **测试样本**：保存可复现的日志、目录和攻击用例。
4. **测试命令**：其他开发者能够重复执行。
5. **原始数据**：保留耗时、内存、CPU、返回值和失败信息。
6. **结论**：给出通过、有限通过或不通过。
7. **影响**：说明是否需要修改需求、架构或默认限制。

预研代码不得直接当作正式实现合并。能够复用的代码应在正式设计完成后重新评审。

## R-02：MCP SDK 和 Streamable HTTP POC

### 待验证问题

- `rmcp` 是否能实现本项目需要的 tools-only Server？
- Streamable HTTP 能否被实际 AI 客户端发现和调用？
- 工具 Schema 和结构化结果能否被客户端正确解析？

### 实验内容

实现仅返回模拟数据的三个工具：

```text
list_log_sources
search_logs
get_log_context
```

要求：

- 使用 Rust 类型生成输入和输出 JSON Schema。
- 返回结构化 JSON，而不是只返回拼接文本。
- 同时提供 stdio 调试入口和 Streamable HTTP 入口。
- 使用 MCP Inspector 检查工具发现、参数 Schema、返回结果和错误输入。
- 使用至少一个项目实际计划采用的 AI 客户端进行远程调用。
- 连续调用、并发调用和客户端断开场景均需测试。

### 重点记录

- `rmcp` 精确版本和启用的 feature。
- 客户端及其版本。
- MCP 协议协商结果。
- 工具输入和输出 Schema。
- 连接、重连和会话行为。
- SDK 对请求取消的暴露方式。
- Host/Origin 校验缺口是否影响目标部署方式。

### 通过标准

- 客户端能够发现并调用三个工具。
- 输入参数错误能够返回清晰的工具错误。
- 结构化日志结果不会被客户端丢失或错误转换。
- 连续 100 次工具调用无协议错误和资源泄漏迹象。
- Streamable HTTP 连接中断不会导致服务进程异常退出。

## R-03：工具 Schema 和客户端可用性

### 待验证问题

- 当前需求中的参数是否容易被 AI 正确调用？
- 工具描述是否足以避免 AI 提交路径、正则表达式或过大参数？

### 实验内容

为三个工具设计候选 Schema，重点比较：

- `source_ids` 的数量限制和描述。
- `keyword` 的最小、最大长度。
- `case_sensitive` 的默认值。
- `start_time`、`end_time` 的 RFC 3339 格式。
- `order` 的枚举值。
- `max_results` 的服务端硬上限。
- `cursor` 与其他查询参数是否允许同时出现。
- `before_lines`、`after_lines` 的上限。

使用自然语言问题驱动客户端调用，例如：

```text
查一下 payment-test 中 requestId=abc123 的日志
查 14:20 前后支付服务的 PaymentAuthException
把该异常后面的堆栈也取出来
继续查看下一批结果
```

### 通过标准

- AI 在主要场景中能够选择正确工具并构造合法参数。
- 工具 Schema 不允许客户端突破服务端硬限制。
- 路径、Shell 和正则样式内容只能作为普通搜索文本，不能改变文件选择逻辑。
- 形成最终工具 Schema 草案并记录需要修改的需求项。

## R-04：安全文件访问

### 待验证问题

- 是否能够从配置的日志根目录安全发现和打开文件？
- 是否能够在存在竞争条件时仍阻止目录逃逸和软链接访问？

### 候选设计

1. 启动或配置加载时，以不跟随软链接的方式打开日志来源根目录。
2. 保存根目录文件描述符，不在查询时重新从任意绝对路径开始解析。
3. 相对根目录调用 `openat2()`。
4. 至少使用：

```text
RESOLVE_BENEATH
RESOLVE_NO_SYMLINKS
RESOLVE_NO_MAGICLINKS
```

5. 打开文件后调用 `fstat`，确认是普通文件。
6. 业务代码禁止使用 `unsafe`；底层系统调用通过经过审查的库封装。
7. 不调用 `grep`、`rg`、`find` 或 Shell。

### 必测用例

- `../etc/passwd`。
- 绝对路径。
- 重复分隔符和 `.`、`..` 组合。
- 最终文件是软链接。
- 中间目录是软链接。
- `/proc` magic link。
- 检查后将普通文件替换为软链接。
- 查询过程中交换目录或文件。
- FIFO。
- Unix Socket。
- 字符设备和块设备（在安全测试环境中模拟或验证拒绝逻辑）。
- 跨挂载点场景，评估是否需要 `RESOLVE_NO_XDEV`。

### 通过标准

- 所有逃逸和软链接用例均不能读取白名单之外的内容。
- 竞争条件测试不能绕过边界。
- 特殊文件均被拒绝。
- 错误信息不返回服务器绝对路径。
- 目标服务器内核和文件系统支持选定方案。
- 若目标内核低于 5.6，必须给出明确 NO-GO 或独立安全方案，不能静默降级。

## R-05：日志扫描器

### 待验证问题

- Rust 实现能否以有限内存扫描大文件？
- 超长行、非法编码和大小写搜索应如何处理？
- 多文件搜索的顺序和结果截断如何实现？

### 候选实现

- 使用固定或可复用缓冲区顺序读取文件。
- 使用字节级字面量匹配，避免为每一行创建多个 String。
- 对单行设置硬上限，超过上限后截断返回，但继续安全跳过剩余内容。
- 不要求整个文件是合法 UTF-8；返回时采用明确的替换或错误策略。
- 搜索达到结果数、响应大小、文件数、字节数或时间限制时停止。
- 搜索顺序必须稳定、可测试。

需要单独决定：

- 不区分大小写是否仅采用 ASCII case folding。
- 是否支持完整 Unicode case folding。
- 非法 UTF-8 是替换、跳过还是返回文件级错误。
- 超长行中位于截断部分的关键字是否仍应被发现。

### 测试用例

- 1 个大文件，关键字位于开头、中间、结尾和不存在。
- 10,000 个小文件。
- 中文关键字。
- 英文大小写变化。
- 32 MB 无换行单行。
- 高频匹配导致结果快速达到上限。
- 文件持续追加。
- 文件读取过程中被截断或删除。

### 通过标准

- 内存占用不随单个日志文件大小线性增长。
- 超长行不会造成无界分配或进程崩溃。
- 结果数量和响应字节数不会突破配置上限。
- 相同输入和静态文件集得到稳定结果顺序。
- 非法编码行为已明确并写入技术决策。
- 大小写语义已明确并写入工具说明。

## R-06：阻塞 I/O、并发、超时和取消

### 待验证问题

- 日志扫描是否会阻塞 Tokio 核心执行线程？
- 请求取消和超时后，底层扫描任务能否及时退出？
- 并发查询是否能够被严格限制？

### 候选设计

```text
MCP / HTTP 层：Tokio 异步任务
日志扫描层：有界阻塞任务池或专用线程池
并发控制：Semaphore
取消：CancellationToken + 扫描循环协作检查
截止时间：Instant deadline
```

扫描循环应在以下位置检查取消和限制：

- 打开下一个文件前。
- 每读取固定字节数后。
- 每产生一批结果后。
- 排序或组装大结果前。

不能假设取消异步 Future 会自动终止已经运行的阻塞扫描任务。

### 测试用例

- 1、4、8 个并发查询。
- 查询开始后主动取消。
- 客户端断开连接。
- 极短超时。
- 达到最大扫描字节数。
- 达到最大扫描文件数。
- 达到最大结果数和响应大小。
- 扫描期间持续执行 MCP ping 或轻量工具调用，观察事件循环延迟。

### 通过标准

- 日志扫描不在 Tokio 核心线程中执行长时间阻塞 I/O。
- 并发任务数量不突破配置值。
- 取消或超时后扫描能够协作退出。
- 目标取消响应延迟不超过 500 ms；若无法达到，必须记录原因并调整检查粒度。
- 查询超时的实际超出量目标不超过 1 秒。
- 扫描任务结束后文件描述符、内存和并发许可均被释放。
- 高负载扫描期间，MCP 控制面仍能响应轻量请求。

## R-07：`match_ref` 和上下文读取

### 待验证问题

- 如何让 AI 读取匹配位置附近内容，同时不开放任意文件和任意行号读取？
- 日志轮转或文件替换后，引用如何安全失效？

### 候选设计

首期优先验证服务端有状态引用：

```text
match_ref -> {
  source_id,
  relative_file_id,
  device_id,
  inode,
  byte_offset,
  line_number,
  created_at,
  expires_at
}
```

`match_ref` 使用随机不可预测标识，实际定位信息保存在服务端内存中。

读取上下文时：

- 根据原日志来源重新进行安全文件打开。
- 校验设备号和 inode。
- 校验引用有效期。
- 校验上下文行数上限。
- 文件已经轮转或替换时使引用失效，而不是读取同名新文件。

### 测试用例

- 正常读取前后上下文。
- 修改 `match_ref`。
- 使用过期引用。
- 文件被轮转。
- 同名文件被替换。
- 文件被截断。
- 服务重启后引用失效。
- 多个并发上下文请求。

### 通过标准

- 客户端不能通过构造引用选择任意文件或任意位置。
- 文件身份发生变化时不会错误读取新文件。
- 引用过期和服务重启行为明确。
- 上下文读取不突破行数和响应大小限制。
- 明确首期是否接受“服务重启后引用失效”。

## R-08：分页游标

### 待验证问题

- 结果截断后如何继续查询？
- 游标是否需要保存完整扫描状态？
- 日志持续变化时，分页是否能保持可理解的语义？

### 对比方案

#### 方案 A：服务端有状态游标

保存：

- 查询条件哈希。
- 来源和候选文件快照。
- 当前文件位置。
- 已消耗限制。
- 创建和过期时间。

优点：实现和安全校验相对直接。  
缺点：服务重启后失效，占用服务端内存，不便多实例部署。

#### 方案 B：签名无状态游标

将位置和查询摘要编码后签名。

优点：服务端状态少。  
缺点：设计复杂，容易暴露实现信息，日志轮转时一致性更难处理。

首期优先验证方案 A。

### 通过标准

- 游标不可预测且不能被篡改后用于其他查询。
- 游标与原查询条件绑定。
- 游标有明确有效期和容量上限。
- 日志变化时的重复、遗漏和失效语义被记录。
- 形成首期采用或暂缓分页的明确决策。

## R-09：时间范围和日志轮转

### 待验证问题

- 不同服务日志时间戳如何配置和解析？
- 多行异常堆栈中无时间戳的行如何处理？
- 未配置时间规则时，文件修改时间能否有效缩小扫描范围？

### 实验内容

至少选取两种真实日志格式，例如：

```text
2026-06-19 14:20:03.125 INFO ...
2026-06-19T14:20:03.125+09:00 ERROR ...
```

验证：

- 时区配置。
- 毫秒和无毫秒格式。
- 多行堆栈续行。
- 无法解析的行。
- 当前日志和日期轮转日志。
- 按文件修改时间预筛选。
- 多来源结果排序。

### 通过标准

- 时间戳规则能够通过配置表达至少两种真实格式。
- 无时间戳续行的处理规则明确。
- 无法解析的时间不得被伪造。
- 未配置规则时明确退化为文件级筛选和稳定顺序。
- 形成是否将行级时间过滤纳入首期的最终决定。

## R-10：性能、稳定性和部署验证

### 基准数据集

至少包含：

| 数据集 | 目的 |
|---|---|
| 单个 1 GB 文件 | 顺序扫描吞吐和内存 |
| 单个 10 GB 文件 | 验证内存不随文件大小增长 |
| 10,000 个小文件 | 文件发现和打开成本 |
| 高频匹配日志 | 结果限制和响应组装 |
| 无匹配日志 | 最坏扫描路径 |
| 32 MB 超长单行 | 无界分配风险 |
| 持续写入日志 | 并发写入稳定性 |
| 轮转和删除日志 | 文件变化稳定性 |

### 测试维度

- 冷缓存和热缓存，无法可靠制造冷缓存时必须注明。
- 并发数 1、4、8。
- 匹配位于文件开头、中间、结尾和不存在。
- 不同缓冲区大小。
- 不同取消检查粒度。

### 采集指标

- 扫描吞吐量。
- 总耗时和首条结果延迟。
- CPU 使用率。
- 峰值 RSS。
- 打开文件描述符数量。
- Tokio 事件循环延迟。
- 取消响应时间。
- 超时超出量。
- 返回结果大小。
- 并发任务数。

### 部署实验

使用 systemd 启动 POC：

- 非 root 用户。
- 日志目录只读。
- 配置目录不可写。
- 限制文件描述符数量。
- 设置内存和 CPU 限制。
- 仅监听指定内网地址。
- 验证优雅停止和重启。

### 通过标准

- 在 10 GB 文件测试中，内存占用与文件大小无关。
- 在预设 cgroup 或 systemd 内存上限下，不发生 OOM。
- 查询限制均可观测且实际生效。
- 并发扫描不会导致进程失去控制面响应。
- 服务可由非 root 用户正常运行。
- 形成基于实测数据的默认限制建议，而不是沿用未经验证的估算值。

吞吐量不设置脱离硬件环境的绝对门槛，但必须记录测试硬件、文件系统、缓存状态和完整数据，以便后续比较 Rust、Go 或不同扫描实现。

## 10. Rust 技术栈决策门槛

### GO

同时满足：

- `rmcp` 能被目标 AI 客户端稳定调用。
- Streamable HTTP 满足当前部署模式。
- 三个工具的 Schema 和结构化结果可正常工作。
- `openat2()` 安全测试全部通过。
- 扫描内存不随文件大小线性增长。
- 超时和取消能够终止底层扫描。
- 资源限制实际生效。
- 不需要大量 `unsafe` 代码。
- 团队能够维护当前 Rust 复杂度。

### CONDITIONAL

出现以下情况之一，但有明确补救方案：

- SDK 某个非核心能力存在缺口。
- Host/Origin 校验需要 Axum 中间件或反向代理补充。
- 游标或行级时间过滤需要推迟到后续版本。
- 需要将目标 Linux 内核提升到 5.6 以上。
- 性能可接受，但默认限制需要比需求文档更保守。

### NO-GO

出现以下任一情况：

- 目标 AI 客户端无法稳定调用 Rust Streamable HTTP Server。
- 路径和软链接边界无法在目标环境可靠保证。
- 目标服务器无法满足安全文件访问所需的内核条件，且没有等价安全方案。
- 请求取消后扫描任务无法受控退出。
- 日志扫描出现不可接受的无界内存或线程增长。
- SDK 核心工具调用在目标客户端中存在无法规避的兼容问题。
- 实现需要大量应用层 `unsafe` 代码。
- 团队无法承担 Rust 的开发和维护成本。

NO-GO 后优先比较 Go 官方 Tier 1 SDK，但安全文件访问、扫描限制和取消能力仍需重新验证，不能假设更换语言即可自动解决。

## 11. 风险清单

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| Rust SDK 当前为 Tier 2 | 协议边角兼容风险 | 只使用 tools 子集；锁定版本；执行客户端和 Inspector 回归测试 |
| SDK Streamable HTTP Host/Origin 校验未完整 | HTTP 入口边界不完整 | 限定内网监听；按需增加 Axum 中间件或反向代理规则 |
| 阻塞扫描占用 Tokio 核心线程 | MCP 无响应 | 使用有界阻塞池并监控事件循环延迟 |
| `spawn_blocking` 任务不能被强制取消 | 超时后仍占资源 | 扫描循环协作检查 CancellationToken 和 deadline |
| 超长单行导致内存增长 | OOM | 限制单行缓冲并使用流式跳过策略 |
| 日志轮转导致引用指向新文件 | 返回错误上下文 | 保存并校验 device/inode；变化后令引用失效 |
| 游标状态占用内存 | 服务状态增长 | TTL、容量上限和 LRU 清理 |
| 时间戳格式不统一 | 时间过滤不准确 | 来源级配置；无法解析时明确退化 |
| `openat2()` 内核版本要求 | 老服务器无法部署 | 预先盘点内核；不允许不安全静默降级 |
| 基准只测热缓存 | 高估生产性能 | 明确缓存状态；在可控环境补充冷缓存测试 |
